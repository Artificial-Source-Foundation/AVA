# AVA 0.2

This is a historical milestone plan for the 0.2 release line. It records the scope boundaries and deferrals used at that point in the project; current capabilities may exceed this document. For current CLI behavior, see `README.md`, `docs/USAGE.md`, and `docs/headless-protocol.md`.

## Goal

Make AVA feel like a usable daily terminal coding agent. The 0.2 focus is TUI polish, visible tool execution, and proving the existing agent tools work well in real coding workflows.

## TUI Direction From M1 Research

### Reference Comparison

- External reference systems provide visual and interaction baselines for composer-first workflow, transcript clarity, slash command palette, visible thinking/progress, tool timeline, and explicit permission prompts.
- Secondary references inform fast/direct feel and compact tool execution cards.
- Historical AVA prototypes are references for prior tool card and permission modal ideas only; do not restore their architecture or code.

### TUI Technology Decision Path

- FTXUI is the strongest external C++ TUI candidate found so far.
- Do not add FTXUI or any new terminal UI dependency by default.
- First define AVA-owned TUI interfaces, rendering tests, and the minimum 0.2 interaction set.
- Then run a small evaluation comparing the current custom terminal path against an FTXUI spike for input handling, layout, redraw behavior, testing, maintenance cost, binary impact, and accessibility of future changes.
- Record the decision before adopting the dependency.

### What Good TUI Means For 0.2

- Daily coding sessions feel calm, readable, and responsive.
- The composer supports practical multiline editing and slash-command discovery without hiding normal chat flow.
- The transcript makes assistant text, visible thinking/progress, tool activity, errors, and truncation easy to scan.
- The TUI remains a presentation layer over backend-enforced permissions and tool execution.
- The slash-command palette owns input collection, candidate display, and rendering only; command parsing, authorization, session mutation, tool execution, and mode changes remain in app command handlers outside the TUI.

### Interaction Direction

- Add a reference-informed slash command palette for common actions such as mode switching, session actions, and safe built-in commands.
- Show thinking/progress visibility without exposing raw internal protocol noise.
- Represent tool and agent activity as timeline cards with name, concise arguments, state, result summary, errors, and expandable details later.
- Use modal-style permission prompts for `ask` decisions with clear command/file context, allow/deny choices, and fail-closed non-interactive behavior.

### 0.3 Backlog Boundary

Keep 0.2 focused on the TUI foundation and existing 0.1 tool loop. A backlog item may move into 0.2 only when it directly blocks a listed 0.2 release criterion, can be implemented as the smallest local support needed for that criterion, does not introduce a new public subsystem or compatibility surface, and is documented in the milestone that needs it.

Hard deferrals for 0.3 or later: theming systems, plugin/TUI extensions, MCP, subagents, multiple providers, LSP, web fetch, automation/print modes, persistent permission-rule management, full session tree UI, rich diff/patch review flows, and any extensibility API beyond the minimal 0.2 TUI/app boundary.

## In Scope

- A cleaner TUI runtime separated from CLI wiring.
- Better transcript rendering and input behavior.
- Reference-informed slash command palette direction for core in-TUI actions.
- Clear status for active agent turns.
- Visible tool calls, tool results, failures, and truncation.
- Interactive permission prompts for `ask` decisions.
- Tool workflow verification for the 0.1 tools: read, write, edit, apply_patch, glob, grep, bash, and question.
- Resume sessions with useful recent transcript context.
- Cancellation or safe interruption for long-running turns where practical.

## Out Of Scope

- Additional providers.
- MCP, plugins, or subagents.
- Full automation CLI modes such as `ava "prompt"` and `--print`.
- LSP and web fetch.
- Full session tree UI.
- Broad architecture rewrite.

Historical note: `--print` and JSONL RPC MVP behavior landed after this scope was written. See `docs/USAGE.md` and `docs/headless-protocol.md` for current behavior.

## Milestones

### M0: Stabilize The 0.2 Release Baseline

- Keep normal tests passing.
- Keep sanitizer tests passing.
- Keep real OAuth smoke working.
- Document the 0.2 scope.

### M1: TUI Runtime Extraction

- Capture the TUI research direction and dependency decision path.
- Move interactive TUI loop code out of `main.cpp`.
- Keep existing behavior unchanged.
- Keep rendering deterministic and testable.
- Preserve non-TTY line-shell fallback.

### M2: Composer And Transcript Polish

- Add better input editing, multiline handling, and viewport behavior.
- Add slash command palette discovery for core actions.
- Show active thinking/progress in a user-readable way.
- Improve terminal resize behavior.
- Keep model and tool output sanitized before rendering.

### M3: Tool Timeline

- Show tool name, argument summary, status, result summary, and errors in the TUI.
- Use compact timeline cards as the baseline tool/agent visibility pattern.
- Keep detailed tool data in the session JSONL.
- Add fake-provider regression tests for tool-display flows.

### M4: Permission Modal

- Support interactive allow/deny for `ask` decisions.
- Present permission prompts as modal-style focused decisions with clear context.
- Keep non-interactive mode fail-closed.
- Persist permission request and resolution events.

### M5: Responsiveness And Cancellation

- Show active turn progress while AVA is working.
- Add a safe cancellation path for provider/tool turns where practical.
- Preserve process timeouts and output limits.

### M6: Tool Audit And Release Hardening

- Smoke every 0.1 tool through the agent loop and TUI.
- Fix discovered tool/schema/display mismatches.
- Run code, security, and docs reviews.
- Pass normal tests, sanitizer tests, and real OAuth smoke.

## Release Criteria

AVA 0.2 is done when:

- The TUI is comfortable for a normal coding session.
- Tool activity is visible and understandable.
- Interactive permission prompts work.
- Existing 0.1 tools are verified through real workflows.
- Real OpenAI OAuth chat still works.
- Normal and sanitizer test suites pass.
- Docs match the shipped behavior.
