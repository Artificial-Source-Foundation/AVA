# AVA 1.1 Backend Planning Notes

Status: planning only. The compiled runtime still reports `1.0.0`; this document does not become release evidence until a dedicated 1.1 implementation and release-bump slice lands.

AVA 1.1 should turn the current 1.0 backend baseline into a stronger backend/runtime for a terminal coding agent. The candidate work is tracked in `docs/product/capabilities-1.1.md` as backend-only planning.

Frontend/TUI planning and implementation are Carlo-owned. AVA backend planning should expose semantic events, RPC commands, session/provider/tool contracts, and safe persistence surfaces that Carlo's frontend can consume without planning UI layout or renderer work here.

## 1.1 Backend Priorities

### P1: Backend Depth For Real Workflows

- Session tree workflows: backend/RPC fork, clone, tree inspection, labels, session names, caller-supplied branch summaries, and session-versioning policy are implemented; provider-generated summaries remain deferred until branch UX defines model-call permission, budget, and stale-session behavior.
- Persistent permission rules with durable allow/deny management and audit semantics are implemented; richer rule UX, diagnostics, and broader policy categories remain follow-up work.
- Unified settings with global/project merge, validation, safe writes, and reload diagnostics.
- Full LSP symbols, definitions, references, bounded on-disk document sync, pull/publish diagnostics, and globally exact-opt-in installed-only built-in recipes are implemented; unsaved-buffer sync remains follow-up work.
- Multimodal/image attachment support across model metadata, session records, provider payloads, and safe textual fallback metadata is implemented; RPC upload/input plumbing and user-facing import flows remain follow-up work.
- Provider/auth breadth: keep Anthropic API-key and stored/env OAuth bearer support, but defer Anthropic interactive OAuth unless Anthropic publishes a documented third-party flow. Gemini native Google Generative AI support exists; Copilot/Bedrock/Vertex/Azure support remains a separately scoped follow-up because each provider needs its own auth, credential-chain, cost, and live-smoke design.
- Plugin core-service proxy so plugins can request AVA-mediated file, shell, network, and session operations through existing permissions.

### P2 Or Research

- HTTP/server daemon mode after stdio RPC remains stable.
- Broader task graphs and public/default parallel ordinary tool execution after replay, permission-audit ordering, cancellation, public opt-in, and UX semantics are designed. Configurable `task` subagents, background job tracking, and an internal default-off read/search parallel AgentLoop option landed after the original 1.0 cut-line and are recorded in product docs.
- Plugin package manager or marketplace after trust, compatibility, and remote-install security are designed.
- OS/container sandboxing only if AVA can make truthful cross-platform guarantees.
- Advanced MCP transports, resource templates, subscriptions, binary/blob resources, and richer resource diagnostics after the 1.0 read-style resource boundary remains stable.

## Acceptance Gate Shape

Before a future 1.1 release bump:

- Backend P1 work has focused CTest coverage, RPC/headless contract tests where applicable, session replay/export validation for persistent data, and `git --no-pager diff --check` clean.
- Security-sensitive changes, especially permission persistence, plugin service proxy, package installs, sandboxing, and provider auth, receive explicit security review.
- `docs/USAGE.md`, roadmap docs, and capability docs reflect implemented behavior rather than aspirational behavior.

## Non-Goals For The First 1.1 Cut

- Matching every Pi or OpenCode feature.
- Frontend/TUI layout, rendering, modals, keybindings, terminal polish, or interaction flows.
- Slack bots, GPU pod orchestration, web artifact workspaces, browser DOM injection, or web-only iframe sandboxes.
- In-process plugin ABI by default; AVA's out-of-process plugin boundary remains the safe default.
- Claiming sandbox guarantees without real OS/container enforcement and tests.

### 2026-05-08: Image Attachment Backend Slice

The backend hardening pass added a guarded image input slice. Session user messages may carry sanitized `attachments[]` metadata containing only canonical unescaped keys for `id`, `type:"image"`, `mime_type`, `byte_size`, `sha256`, `storage_path`, and optional `redacted`; `byte_size` must be an unquoted base-10 JSON integer literal from `1` through `20971520`, and fractions, exponent notation, strings, inline bytes, unknown fields, duplicate keys/ids, assistant attachments, unsupported MIME types, and non-`attachments/...` storage paths are invalid. Provider replay reconstructs text fallback labels plus provider-neutral image content parts, model switching rejects targets that cannot replay image input, fork/clone copies verified attachment files, and provider calls load bytes only from AVA-managed `<session_id>.attachments` storage after path, symlink, byte-size, and SHA-256 checks. OpenAI Responses, OpenAI-compatible chat-completions, and Anthropic Messages serialize verified image payloads; request validation caps image count and aggregate bytes, and Anthropic applies its lower per-image byte limit. RPC upload/input flows and frontend/TUI attachment UX remain deferred.

### 2026-05-08: LSP Code Intelligence Backend Slice

The backend hardening pass expanded LSP beyond diagnostics. AVA now exposes capability-gated backend tools for diagnostics, document symbols, workspace symbols, definitions, and references. Queries use bounded on-disk full-text `textDocument/didOpen` and versioned `didChange` synchronization. Explicit `$AVA_CONFIG_DIR/lsp.json` and workspace `.ava/lsp.json` files configure language servers with strict `version:1`, unique server ids, exact `argv[]`, optional `file_extensions[]`, optional `language_id`, and bounded timeouts; server launch is lazy and requires high-risk `lsp.server.launch` approval. Provider-visible LSP errors are redacted and results are bounded and workspace-relative where possible. Workstream 7 was narrowed to one default-off, global exact-opt-in installed-only `clangd` recipe with non-hardlinked owner/mode/inode/size/ctime executable sealing, identity-bound permission, bounded per-root routing/cache, passive private status, and bounded pull/centrally dispatched publish diagnostics. Automatic `gopls` and `rust-analyzer` recipes are deferred until separately approved verified containment/offline designs; explicit configuration remains available. Project opt-in, downloads/managers, workspace-local executables, unsaved-buffer sync, and frontend/TUI presentation remain excluded or deferred.

### 2026-07-05: Configurable Task Subagents

AVA added an OpenCode-style model-visible `task` tool backed by native C++ child sessions. Built-in subagents are `general` and read-only `explore`; custom Markdown subagents load from global and trusted project `agents/` directories with bounded frontmatter/body parsing. The `task` tool asks explicit `TaskRun` permission, records parent/child session evidence, links child sessions through metadata, hides recursive `task` from child tool schemas, and supports `--allow-tool task` in headless policy. Deterministic coverage lives in `ava_tests.agent_loop` and `ava_tests.app_print`; live coding dogfood covers skill/read/edit permission behavior when credentials are present.

### 2026-07-06: Background Job Registry And Base Prompt Metadata

Background `task` subagents moved from fire-and-forget threads to a runtime-owned `BackgroundJobRegistry` with `job_id`, running/terminal snapshots, cancellation, retained bounded results, join-on-shutdown behavior, and explicit running/retention limits. Background children use fresh provider/transport instances, do not inherit parent UI callbacks or LSP providers, and require the runtime-owned registry to be present. The same slice replaced duplicate runtime prompt text with `RuntimeBasePromptMetadata`; the effective system prompt remains the single prompt-text owner while `/context` reports base prompt source, byte count, and fingerprint. Persisted JSONL `session_start` entries keep the prompt override boolean and loaded context-source metadata; runtime/RPC `session_start` events expose only `mode`, `provider`, and `model`.
